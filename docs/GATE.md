# Gate C: the sandbox pre-tool gate

`SOURCE_MODE=live_sandbox_gate` switches the sandbox from advice to enforcement for write and payment tools (`payments.execute`, `email.send`). Before a gated tool call:
1. The tool wrapper calls `POST /v1/preflight`.
2. The server records the pre_tool event and decides it synchronously, within a budget of 600 ms in total and 400 ms for the judge (RFC §6.5).
3. It issues a **ControlDecision bound to exactly that call**: tenant, run, tool, operation id, the args digest, the authorization version, a 30 s expiry, and a single-use nonce.
4. The gateway **loads the control itself, re-verifies every binding and the current authority state, and consumes the nonce in the same transaction as the side effect.**

Only a `not_executed` receipt under a deny or hold control is counted as *prevented*.

- **F1 in gate form** (`f1-gate-judge-timeout`): the judge call for the payment really aborts on a 1 ms budget. The payment is held (`judge_unavailable`) and not executed; the read-only lookup is not gated.
- **Hard-rule decisions** (S3 over the limit, S4 no approval, S6 outside the domain) never need the judge. They are denied or held and never executed, and no side effect is written.
- **"Prevented" counts every not_executed call under a deny or hold control.** That includes fail-closed holds of *benign* calls when the judge ran out of budget. It is the RFC §2 definition ("the call did not happen"), not a count of attacks stopped.
- **A cold start slows the gate judge but stays inside the budget.** So does sharing the GPU with a shadow judge under this scenario load.
- **Saturating the same GPU with a Kev-4B workload pushed the gate judge to the budget.** In the recorded saturated run (the `gate-judge-while-kev4b-saturated` row above), judged preflights reached the budget, and some benign judged payments were **held** (`judge_unavailable`) instead of allowed. The row's allowed and prevented counts show how many. An earlier, unrecorded run under the same kind of contention held every judged payment. Either way, the gate **failed closed**: held, never silently allowed. That is safe, but it blocks legitimate work.
- **Deployment rule that follows:** give the gate judge its own accelerator (or run the shadow judge elsewhere), and watch `/v1/metrics` `gate.sdk_preflight_ms` and the rate of `judge_unavailable` holds.

## What the gate does not do yet

Semantic signals are uncalibrated (see `docs/EVAL.md`), so they never block. S2 (payee mismatch) and S7 (goal deviation) are **allowed** in gate mode today. What blocks is:
- hard rules;
- missing or stale evidence;
- a required judge signal that is unavailable.

Review resolution (a human approving a held call) is not implemented. A held call stays unexecuted.
