# 为什么选择 Kev 作为默认 judge（2026-09-29）

> 依据：构建计划 D2（[`logs/2026-09-28_BUILD_PLAN.md`](../../logs/2026-09-28_BUILD_PLAN.md)）、spike 记录（[`runs/spike-2026-09-28/`](../../runs/spike-2026-09-28/)）、Kev README 与 model card（`jaredpalmer/kev@3e1cd3b`）。
> 相关：[Kev 的训练数据](2026-09-29_KEV_TRAINING_DATA.md) · [专有数据收集与微调计划](2026-09-29_PROPRIETARY_DATA_AND_FINETUNE_PLAN.md)

## 结论

Kev 是目前唯一**开放、可本地运行、且与 Jev 协议一致**的 Jev 类判别模型。它让本项目在没有 TypeSafe key 的情况下，用真实模型跑通整条实时链路，并且可以用自己的数据继续微调。

## 理由

1. **协议与 Jev 相同。** Kev 实现 TypeSafe System One 的 `/v1/systemone` 接口。本项目用同一个 client 和同一个校验器服务两个后端，切换到 TypeSafe 托管 Jev 只需配置（`JUDGE_BACKEND=typesafe` + `TYPESAFE_API_KEY`）。
2. **开放、可本地部署。** Apache-2.0，Hugging Face 权重不设门槛，有 0.8B / 4B / 9B / 27B 四档，Mac 的 MLX 或单张 GPU 即可运行。本项目没有 TypeSafe key，Kev 是唯一真实可用的后端。
3. **适合实时链路。**
   - 判别模型：一次前向传播给出每个问题的概率分布，不做文本生成；
   - 自带温度校准（本机 Kev-4B 报告的温度为 2.406）；
   - 本机（Apple M4 Pro，MLX，bf16）实测 HTTP 往返 p50：Kev-0.8B 151 ms，Kev-4B 857 ms（见 [`docs/EVAL.md`](../EVAL.md)）。0.8B 放得进 gate 模式 400 ms 的 judge 预算。
4. **可以微调。** 自带 `kev.train --init_from`，从已发布 checkpoint 出发做 LoRA 增量训练，对应项目"用开源数据训练/微调"的要求（D3）。
5. **与 Jev 的差距不大（Kev 官方数据，dev/test）。** 在训练中从未出现过的数据源上：Kev-4B 0.817 / 0.838，Kev-27B 0.848 / 0.896，Jev 0.857（仅 dev）。Kev 作者注明这不是受控对比，因为 Jev 的训练数据未知。

## 已知局限

- **开箱即用的 Kev-4B 在 agent 安全问题上偏弱。** spike 测试中，一段明显注入的供应商备注，`instruction_override` 只有 0.296，`goal_deviation` 0.484。这正是做开源数据微调和评测的直接原因。
- **因此语义策略保持 `experimental`**：信号只记录、不改变线上建议。拦截只来自硬规则、证据缺失或必需信号不可用。
- **模型名不代表身份。** Kev 在 `kev-latest` 和 `jev-latest` 两个名字下提供同一个模型，所以 `judge_source` 一律取自 `/v1/models` 的 `run` 字段。
- **上下文长度。** Kev 训练时 state 最长 384 token，所以 judge 视图默认限制在 1,024 token 以内（D6），按后端可调。
- **Kev 必须与服务端同机并绑定 127.0.0.1**，因为 `kev-local` 后端不向 judge 发送凭证。
