**User request:** "JEV demo 中「人工参与给出判断 → 强化学习对齐人工判断 → 自进化KEV模型」是最好的卖点，但页面上看不出来，帮我设计方案来展示自进化模型对优化结果正面影响。" In English: the strongest selling point is the loop where people give judgments, training aligns Kev with them, and Kev improves itself. The pages don't show it. Design a way to show the self-improving model's positive effect on results.

## 0. What exists, and what is true

**The loop exists in code end to end**, but no page tells it as a story.

| Step | Where | Status |
|---|---|---|
| A held action asks a person atomic questions; Allow or Deny records one `human_reviewed` label per answer | console review queue (USER_MANUAL §"review", `docs/USER_MANUAL.md:364`) | built, live console |
| Labels become Kev training JSONL: time-based split, state groups never cross splits, test split is `human_reviewed` only | `eval/export/labels-to-kev.ts` | built (T6) |
| LoRA fine-tune of Kev, time-boxed | `eval/finetune/finetune.sh` | built, run three times |
| Held-out eval and report, generated, with drift tests | `eval/run/*`, `docs/EVAL.md` Results | built |
| A promotion gate (only a better model goes live) | — | **not built**; the docs say calibrations are "recorded and not activated" |

**Measured effect** (`docs/EVAL.md`, block generated by `eval/run/summary-md.ts`; held-out AgentDojo test, 250 items, never seen in training):

| model | instruction_override AUROC | goal_deviation AUROC | goal_deviation recall @ cal. threshold · FPR | p50 latency |
|---|---|---|---|---|
| Kev-0.8B as released | 0.602 | 0.893 | 0.400 · 0.014 | 151 ms |
| Kev-0.8B fine-tuned | 0.973 | 0.961 | 0.800 · 0.009 | 149 ms |
| Kev-4B fine-tuned (same recipe) | 0.953 | 0.666 | 0.229 · 0.126 | 913 ms |

**Honesty constraints** (these go on every surface, in plain words):
1. **The labels came from benchmarks, not from people.** The measured gain came from **open-benchmark labels** (`benchmark_ground_truth_derived`), not from customer reviewers. The human-label path is built, but no fine-tune on human labels has been run.
2. **The method is fine-tuning, not reinforcement learning.** It is supervised LoRA fine-tuning, not RL. The user's phrase "强化学习对齐" becomes "trained to agree with reviewers (fine-tuning on their labels)". RL (for example DPO or GRPO on reviewer preferences) is listed as a later step, not claimed.
3. **Not every retrain helps.** The same recipe made Kev-4B *worse* on goal_deviation. We show this as the reason the promotion gate exists, which is a selling point (the loop is safe because it is gated), not something to hide.
4. **The EVAL.md caveats carry over:** a residual style risk on AgentDojo, and calibrations not activated.
5. **Interactive parts are simulated** and say so, like the rest of the demo.

## 1. The story on the page (what the user sees)

### 1a. Demo page: a new top tab, **Learning loop**, after Policy Studio

Same header, simulated badge and tab styles as Live, Replay, Policy Studio and About.

1. **Loop strip** (top, one row, clickable stages):
   - **Held for review → Reviewer answers → Labels → Train Kev → Gate (held-out test) → Promote**;
   - each stage shows a live count from this session;
   - the active stage is highlighted as the user moves through 2–4 below.
2. **Review inbox (simulated):**
   - the runs this session held for review (from Live: the REVIEW and HOLD verdicts, for example SOC5's 2nd and 3rd suspension, the AP scenarios that hold);
   - each item asks its atomic questions in plain words (the battery's own `QUESTIONS_BY_AGENT` texts), with Yes/No per question and Allow/Deny;
   - each answer becomes a label chip ("human_reviewed · simulated").
   - **"Auto-answer the rest as a careful reviewer would"** fills the remaining answers from the scenario's ground truth, so a presenter can move fast.
   - The counter shows labels gathered toward a training batch.
3. **Train (simulated):**
   - **Train Kev v2** is enabled once the batch has ≥ N labels (N = 12, the number the scripted scenarios yield; computed, not typed);
   - a short progress animation;
   - then a model card: base `kev-0.8b`, method "LoRA fine-tune on reviewer labels", label count, wall time (illustrative, sized to the measured 39 min, labelled).
4. **Gate:**
   - v1 and v2 are scored on a **held-out simulated set** that the review inbox never touched, built from the domains' benign and attack variants with ground truth;
   - **pass rule:** recall up and false-holds not up, at the calibrated threshold;
   - **Promote** is enabled only on a pass;
   - a **"Show a failed retrain"** toggle replays the Kev-4B lesson: a model that got worse is blocked at the gate, with that text.
5. **Before and after on the same runs** (the payoff). After Promote, the user's own session runs are replayed under v2, side by side with v1. Per run, the step verdict changes with the reason ("v1: Held for review · v2: Blocked, goal_deviation 0.91" or "v1: Held for review · v2: No objection, ran"). Three outcome tiles summarise it:
   - **Catches:** true attacks stopped before running, v1 → v2;
   - **Reviewer load:** actions sent to a person, v1 → v2, which should fall;
   - **False holds:** benign actions held, v1 → v2.
6. **Measured evidence card** (always visible at the bottom of the tab; not simulated):
   - the table from §0 with "measured · held-out AgentDojo · benchmark labels";
   - the three honesty lines above;
   - a link to `docs/EVAL.md`.
   - The numbers come from a generated JSON (§2), never typed.

**Simulation model** (written in code and in About, reviewable):
- v1 scores are today's demo engine scores.
- v2 moves the score of each question family covered by reviewer labels toward the label: `s' = s + k·(y − s)`, with `k` chosen once so the simulated held-out recall and FPR gain is **no larger** than the measured 0.80 / 0.009 versus 0.40 / 0.014 change.
- Families with no labels do not move. That shows the loop learns *what reviewers taught*, and the Gate's "failed retrain" flips `k` to a harmful value.
- All of it is deterministic per seed.
