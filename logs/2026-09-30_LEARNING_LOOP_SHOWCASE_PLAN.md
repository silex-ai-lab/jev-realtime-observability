## 0. What exists, and what is true

**The loop exists in code end to end**, but no page tells it as a story.

| Step | Where | Status |
|---|---|---|
| A held action asks a person atomic questions; Allow or Deny records one `human_reviewed` label per answer | console review queue (USER_MANUAL §"review", `docs/USER_MANUAL.md:364`) | built, live console |
| Labels become Kev training JSONL: time-based split, state groups never cross splits, test split is `human_reviewed` only | `eval/export/labels-to-kev.ts` | built (T6) |
| LoRA fine-tune of Kev, time-boxed | `eval/finetune/finetune.sh` | built, run three times |
| Held-out eval and report, generated, with drift tests | `eval/run/*`, `docs/EVAL.md` Results | built |
| A promotion gate (only a better model goes live) | — | **not built**; the docs say calibrations are "recorded and not activated" |

**Measured effect** (`docs/EVAL.md`, block generated by `eval/run/summary-md.ts`; held-out AgentDojo test, 250 items, never seen in training):

| model | instruction_override AUROC | goal_deviation AUROC | goal_deviation recall @ cal. threshold · FPR | p50 latency |
|---|---|---|---|---|
| Kev-0.8B as released | 0.602 | 0.893 | 0.400 · 0.014 | 151 ms |
| Kev-0.8B fine-tuned | 0.973 | 0.961 | 0.800 · 0.009 | 149 ms |
| Kev-4B fine-tuned (same recipe) | 0.953 | 0.666 | 0.229 · 0.126 | 913 ms |

**Honesty constraints** (these go on every surface, in plain words):
1. **The labels came from benchmarks, not from people.** The measured gain came from **open-benchmark labels** (`benchmark_ground_truth_derived`), not from customer reviewers. The human-label path is built, but no fine-tune on human labels has been run.
2. **The method is fine-tuning, not reinforcement learning.** It is supervised LoRA fine-tuning, not RL. The user's phrase "强化学习对齐" becomes "trained to agree with reviewers (fine-tuning on their labels)". RL (for example DPO or GRPO on reviewer preferences) is listed as a later step, not claimed.
3. **Not every retrain helps.** The same recipe made Kev-4B *worse* on goal_deviation. We show this as the reason the promotion gate exists, which is a selling point (the loop is safe because it is gated), not something to hide.
4. **The EVAL.md caveats carry over:** a residual style risk on AgentDojo, and calibrations not activated.
5. **Interactive parts are simulated** and say so, like the rest of the demo.

## 1. The story on the page (what the user sees)

### 1a. Demo page: a new top tab, **Learning loop**, after Policy Studio

Same header, simulated badge and tab styles as Live, Replay, Policy Studio and About.

1. **Loop strip** (top, one row, clickable stages):
   - **Held for review → Reviewer answers → Labels → Train Kev → Gate (held-out test) → Promote**;
   - each stage shows a live count from this session;
   - the active stage is highlighted as the user moves through 2–4 below.
2. **Review inbox (simulated):**
   - the runs this session held for review (from Live: the REVIEW and HOLD verdicts, for example SOC5's 2nd and 3rd suspension, the AP scenarios that hold);
   - each item asks its atomic questions in plain words (the battery's own `QUESTIONS_BY_AGENT` texts), with Yes/No per question and Allow/Deny;
   - each answer becomes a label chip ("human_reviewed · simulated").
   - **"Auto-answer the rest as a careful reviewer would"** fills the remaining answers from the scenario's ground truth, so a presenter can move fast.
   - The counter shows labels gathered toward a training batch.
3. **Train (simulated):**
   - **Train Kev v2** is enabled once the batch has ≥ N labels (N = 12, the number the scripted scenarios yield; computed, not typed);
   - a short progress animation;
   - then a model card: base `kev-0.8b`, method "LoRA fine-tune on reviewer labels", label count, wall time (illustrative, sized to the measured 39 min, labelled).
4. **Gate:**
   - v1 and v2 are scored on a **held-out simulated set** that the review inbox never touched, built from the domains' benign and attack variants with ground truth;
   - **pass rule:** recall up and false-holds not up, at the calibrated threshold;
   - **Promote** is enabled only on a pass;
   - a **"Show a failed retrain"** toggle replays the Kev-4B lesson: a model that got worse is blocked at the gate, with that text.
5. **Before and after on the same runs** (the payoff). After Promote, the user's own session runs are replayed under v2, side by side with v1. Per run, the step verdict changes with the reason ("v1: Held for review · v2: Blocked, goal_deviation 0.91" or "v1: Held for review · v2: No objection, ran"). Three outcome tiles summarise it:
   - **Catches:** true attacks stopped before running, v1 → v2;
   - **Reviewer load:** actions sent to a person, v1 → v2, which should fall;
   - **False holds:** benign actions held, v1 → v2.
6. **Measured evidence card** (always visible at the bottom of the tab; not simulated):
   - the table from §0 with "measured · held-out AgentDojo · benchmark labels";
   - the three honesty lines above;
   - a link to `docs/EVAL.md`.
   - The numbers come from a generated JSON (§2), never typed.

**Simulation model** (written in code and in About, reviewable):
- v1 scores are today's demo engine scores.
- v2 moves the score of each question family covered by reviewer labels toward the label: `s' = s + k·(y − s)`, with `k` chosen once so the simulated held-out recall and FPR gain is **no larger** than the measured 0.80 / 0.009 versus 0.40 / 0.014 change.
- Families with no labels do not move. That shows the loop learns *what reviewers taught*, and the Gate's "failed retrain" flips `k` to a harmful value.
- All of it is deterministic per seed.

## r2: resolutions of plan review r1 (these supersede §0–§3 where they differ)

r1 review: `reviewer-codex` PLAN-CHANGES (8 items), `coder-deepseek` PLAN-CHANGES (3 required, 6 notes; it re-derived every §0 number from the run files and found them correct). Every item is taken.

**A. The simulated model actually learns, with no oracle** (Codex 1).
- **Model:** v2 = v1 plus a small **logistic correction per Boolean question**:

  `s₂ = σ(logit(s₁) + b_q + Σ_f w_{q,f}·x_f)`

  - The features `x_f` are exactly the feature subset `jev-sim.js` already reads for that question (named per question in code).
  - `w` and `b` are fitted **only on the labels the user collected**, by a fixed, documented procedure: plain gradient descent, a fixed learning rate and step count, L2, all chosen *before* any held-out scoring and written as constants.
- **Frozen:** the parameters are frozen after Train.
- **Held-out scoring** reads features only, never labels.
- **No tuning against the held-out set:**
  - r1's "k sized to the measured gain" is dropped;
  - the simulated numbers are whatever this procedure yields on the authored sets, shown only as simulated, never next to the measured numbers as if comparable.
- **Failed retrain:** "Show a failed retrain" trains with a documented bad setting (labels flipped on one family, which models a mislabelled batch). The gate catches it on held-out.

**B. Authored truth, Boolean questions only** (Codex 2; DS note on held-out).
- **Training scope:** only the battery's **Boolean (noul)** questions per agent are asked and trained. The score and choice questions (`impact`, `attack`) are shown read-only with "not trained in this demo".
- **New fixture:** `web/demo/js/learning/curriculum.js` holds, per domain:
  - **Review examples:** spans and per-question truth for the inbox, labelled "demo-author truth".
  - **Held-out variants:** a disjoint list of benign and attack variants with per-question truth and the expected *correct gateway outcome*. They are never shown in the inbox.
    - A test asserts no state overlap with the review examples or the Live scenarios.
    - The set includes **ambiguous items that v1 gets wrong**, so learning has something to fix.
- **Auto-answer** fills answers from this authored truth, and says so.

**C. Batch size N** (Codex 3; DS 1).
- The Learning tab has its own **"Load review examples"** action. It enqueues the curriculum's review examples for the current domain, alongside any actions held in this session's Live tab.
- **N** is the count of Boolean questions in the curriculum examples for that domain, **computed in code**; the UI shows "x of N answered".
- r1's "N = 12" is withdrawn.
- **Domain switch:** it resets the learning session (the page reloads), with a one-line notice.

**D. Engine hook; Live untouched** (Codex 4).
- **Router:** `router.js` gets an optional `scorer` argument, which defaults to today's `judgeBattery`, **identical by construction**. The AP envelope fixture must stay byte-identical, so Live is unchanged.
- **Re-running under v1 and v2** goes through the same `runStream` with a frozen policy, fault, seed and per-trace history, so hard rules, outages, `combine` and mode mapping keep precedence.
- **Promote** applies v2 **only inside the Learning tab's comparison**, for this simulated session. Live keeps v1. The copy says this.

**E. Metrics that mean something** (Codex 5).
- Metrics are computed on the **held-out variants**, judge-decided boundary only.
- Items decided by a hard rule (`decided_by: rule`) are shown as **unchanged and correct** ("a model can't override these") and are excluded from every learning metric.
- **Definitions** (gate mode; actions taken from real envelopes):
  - **Missed attacks** = attack variants whose action is `allow`, ÷ attack variants.
  - **Reviewer load** = all variants sent to a person (`hold_for_review`), ÷ all variants.
  - **False holds** = benign variants held or blocked, ÷ benign variants.
  - **Gate pass rule:** missed attacks not up, false holds not up, and at least one of them strictly down. Same policy and thresholds for v1 and v2.
- **Per-run reason strings** in the before/after view are computed from the v1 and v2 scores, never typed.

**Build notes from r2** (non-blocking, binding on the build):

1. **The learner:**
   - it fits on `p` (the proposition probability), never on `risk`, and recomputes `risk`, `confidence` and `margin` after (so `grounded`, with `risk: 1-p`, stays right);
   - it clamps before the logit;
   - it uses a documented finite encoding of numeric, Boolean and null features;
   - all preprocessing, optimizer and L2 constants are fixed before any evaluation;
   - a family with no labels returns its original answer exactly.
2. **The v2 scorer:**
   - wraps `judgeBattery`, transforming only eligible, successful Boolean answers;
   - fault status, reduced batteries, latency, token fields and untrained answers pass through;
   - it never receives the fixture truth.
3. **Candidate snapshot:** labels, parameters, policy, faults and seed are frozen together. Edits after Train need a new Train.
4. **Labels:**
   - identity is (example, question), so a reload or a re-answer updates rather than increments;
   - "x of N" counts only valid curriculum Boolean labels;
   - scripted (demo-author) answers and manual answers are marked differently;
   - Auto-answer appears only where authored truth exists;
   - Allow/Deny says it never releases the tool call.
5. **Eligibility for metrics:** semantically evaluated pre_tool variants with no rule or fallback decision. ALLOW outcomes (`decided_by: policy`) stay in the denominators. v1 and v2 use one paired set, in gate mode.
6. **Curriculum authoring:**
   - the ambiguous held-out items must have errors the question's feature subset can express linearly, so a pass path exists in both domains, proven in the build;
   - the failed-retrain family is a documented constant, labelled as a mislabelled toy batch, not a reproduction of the 4B run.
7. **`impact` and `attack`** render identically under v1 and v2.
8. **Evidence link:** no link to `docs/EVAL.md` from the page (it is outside the web root). The evidence details live in the JSON and render on the page, and the source path is shown as text.
9. **The domain switch's `location.assign`** must carry `tab`.
10. **`learning-evidence.json` contract** (DeepSeek writes it; Codex reads it; full precision; display formatting only in the UI):
    - `generated_by`, `sources{}` (repo paths), `hardware`;
    - `test{benchmark, items, positives{q}}`;
    - `models{"kev-0.8b"|"kev-0.8b-ft"|"kev-4b"|"kev-4b-ft": {label, judge_source, instruction_override{auroc}, goal_deviation{auroc, threshold|null, recall, recall_ci[2], fpr}, latency{p50_ms, p95_ms, n}}}`;
    - `finetune{"kev-0.8b"|"kev-4b": {method, epochs, lr, records_total, records_used, wall_s}}`;
    - `caveats[]` (the EVAL.md "What these numbers do not show" points, as short strings);
    - `label_provenance` (`benchmark_ground_truth_derived`, `heuristic_derived`).
